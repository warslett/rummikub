# Code Review

## Overview

This changeset extends the Rummikub game from 2-player-only to supporting 2-4 players. The core changes include: refactoring shared types from singular opponent fields to an `opponents: OpponentInfo[]` array, updating server game logic for multi-player scoring/stalemate/turn rotation, updating Socket.IO handlers for multi-player join/spectate flows, updating all client pages (Lobby, GameBoard, SpectateBoard, GameOver) to render multiple opponents, and adding E2E tests for multi-player scenarios.

## Findings

### [Severity: High] Bug: `playerNames` sent to joining player includes their own name

**File**: `packages/server/src/handlers.ts:57`

**Issue**: The `state` variable is captured on line 44 before `addPlayer()` is called on line 51. Since `getState()` returns a reference to the mutable state object (not a copy), `state.players` on line 57 includes the newly added player. This means the joining player receives their own name in the `playerNames` array.

In the Lobby, `joinedPlayerNames` is set to `data.playerNames`, and `totalPlayers = joinedPlayerNames.length + (hasJoined ? 1 : 0)`. Since the joining player's name is included in `playerNames`, the count is inflated by 1. For example, when Bob joins Alice's game, Bob sees "3/4 players" instead of "2/4 players".

**Suggestion**: Capture `playerNames` before calling `addPlayer`, or filter out the joining player:

```typescript
// Option A: capture names before adding the player
const playerNames = state.players.map((p) => p.name);
game.addPlayer(playerId, playerName);
// ...
socket.emit("game:joined", { playerId, playerNames });

// Option B: filter after (less clean)
const playerNames = state.players.filter((p) => p.id !== playerId).map((p) => p.name);
```

Option A is cleaner — move line 57 to before line 51.

### [Severity: High] Bug: Disconnected opponent status not initialized from server state

**File**: `packages/client/src/pages/GameBoard.tsx:53,80-96`

**Issue**: The `disconnectedOpponents` state is initialized as an empty `Set<string>` and only updated via `player:disconnected`/`player:reconnected` events. If an opponent was already disconnected when the component mounted (e.g., after a page refresh or reconnection), the Set would be empty and the opponent would appear connected. The `opp.connected` field from `gameState.opponents` (which is accurate) is completely ignored.

The same issue exists in `SpectateBoard.tsx` — the old code correctly used `p.connected` from the server state, but the new code replaced it with a local `disconnectedPlayers` Set that has the same initialization problem.

**Suggestion**: Use the `connected` field from the server-provided state instead of (or in addition to) the local event-based tracking:

For GameBoard.tsx, replace:
```tsx
disconnected={disconnectedOpponents.has(opp.id)}
```
with:
```tsx
disconnected={!opp.connected || disconnectedOpponents.has(opp.id)}
```

Or better, derive the disconnected state entirely from `gameState.opponents`:
```tsx
disconnected={!opp.connected}
```

And remove the `disconnectedOpponents` state entirely, since the game state is updated by the server on every state change and includes the `connected` field.

For SpectateBoard.tsx, revert to using `p.connected` from the spectator state:
```tsx
<span className={`text-sm ${!p.connected ? "text-red-400" : "text-gray-400"}`}>{p.name}</span>
{!p.connected && <span className="text-red-400 text-xs">(disconnected)</span>}
```

### [Severity: Medium] Missing type definition for `game:playerJoined` event

**File**: `packages/shared/src/types.ts`

**Issue**: A new Socket.IO event `game:playerJoined` with payload `{ playerName: string }` was added to the server (`handlers.ts:59`) and consumed by the client (`Lobby.tsx:26,38,43`), but no corresponding type definition (e.g., `GamePlayerJoinedPayload`) was added to the shared types. This breaks the project convention of defining all event payloads in shared types.

**Suggestion**: Add a type definition in `packages/shared/src/types.ts`:
```typescript
export interface GamePlayerJoinedPayload {
  playerName: string;
}
```
Export it from `packages/shared/src/index.ts` and use it in both the server handler and the client Lobby.

### [Severity: Medium] `anyPlayerDisconnected` disables all actions even when only one opponent is disconnected

**File**: `packages/client/src/components/GameBoard.tsx:193-228`

**Issue**: In a 3+ player game, if one opponent disconnects, the `anyPlayerDisconnected` flag disables all action buttons (Play, End Turn, Draw, Pass) for the current player. This means the game effectively pauses for everyone when any single player disconnects, even though the other opponents are still connected and the game could continue.

In the 2-player version this made sense (you can't play without your only opponent), but in a 3-4 player game it's overly restrictive.

**Suggestion**: Consider only disabling actions when the current turn belongs to a disconnected player, or when all opponents are disconnected. At minimum, this should be a conscious design decision documented in the plan. For now, a reasonable approach:

```typescript
const currentTurnPlayerDisconnected = !isYourTurn && gameState.opponents.find(
  (o) => o.id === gameState.currentTurnPlayerId && !o.connected
);
```

### [Severity: Medium] Indentation inconsistency in stalemate handler

**File**: `packages/server/src/handlers.ts:225-247`

**Issue**: The `if (scores)` block on line 227 is at the same indentation level as the `const scores` on line 226, but it should be indented one more level since it's inside the `if (state.phase === "ended")` block. This is a pre-existing issue that was carried forward during the refactor, but since this code was modified in this changeset, it should be fixed.

```
      if (state.phase === "ended") {
        const scores = game.calculateStalemateScores();
      if (scores) {           // ← should be indented one more level
        game.applyScores(scores);
```

**Suggestion**: Fix the indentation:
```typescript
      if (state.phase === "ended") {
        const scores = game.calculateStalemateScores();
        if (scores) {
          game.applyScores(scores);
          // ...
        }
        return;
      }
```

### [Severity: Low] `loserMap.get(p.id)!.penalty` uses non-null assertion

**File**: `packages/server/src/handlers.ts:239,372`

**Issue**: The `loserMap.get(p.id)!.penalty` uses a TypeScript non-null assertion (`!`). While this is safe in practice (the map is built from the same `scores.losers` array that contains all non-winner player IDs), the non-null assertion could mask a future bug if the logic changes.

**Suggestion**: Use a safer pattern:
```typescript
const loserInfo = loserMap.get(p.id);
score: p.id === scores.winnerId ? scores.winnerScore : (loserInfo?.penalty ?? 0),
```

Or assert with a meaningful error:
```typescript
const loserInfo = loserMap.get(p.id);
if (!loserInfo) throw new Error(`Missing loser info for player ${p.id}`);
```

### [Severity: Low] Lobby `joinedPlayerNames` could accumulate duplicates

**File**: `packages/client/src/pages/Lobby.tsx:26-28`

**Issue**: The `onPlayerJoined` handler appends to `joinedPlayerNames` without checking for duplicates. If a `game:playerJoined` event is received multiple times (e.g., due to Socket.IO reconnection), the same player name would appear multiple times in the list.

**Suggestion**: Add a duplicate check:
```typescript
function onPlayerJoined(data: { playerName: string }) {
  setJoinedPlayerNames((prev) => 
    prev.includes(data.playerName) ? prev : [...prev, data.playerName]
  );
}
```

## Summary

The changeset successfully implements the core multi-player support (2-4 players) with proper type refactoring, server logic updates, and client rendering changes. The shared types, server game logic, and client components are all consistently updated to use the `opponents: OpponentInfo[]` pattern.

However, there are two High-severity bugs:
1. The `playerNames` array sent to joining players incorrectly includes their own name, causing an inflated player count display.
2. The disconnected opponent tracking uses a local event-based Set instead of the server-provided `connected` field, causing opponents who were already disconnected on component mount to appear connected.

There are also Medium-severity issues: a missing type definition for the new `game:playerJoined` event, 7 missing E2E test cases from the plan, overly restrictive action disabling when any player disconnects in multi-player, and an indentation issue in the stalemate handler.

| Severity | Count |
|----------|-------|
| Critical | 0 |
| High | 2 |
| Medium | 4 |
| Low | 3 |
| Nit | 2 |

## Verdict

CHANGES_REQUESTED

The two High-severity bugs (inflated player count for joining players, and disconnected status not initialized from server state) need to be fixed before this can be merged. The Medium-severity issues (missing type, missing E2E tests, overly restrictive disconnect handling) should also be addressed but are less urgent.
